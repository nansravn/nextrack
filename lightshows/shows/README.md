# shows/ — the show language

A **show** is one night written as data: a palette, named looks, rules, and one cue list per
track, in set order. A compiler turns it into the per-track choreographies of
[`lightshows/tracks/`](../README.md#choreography-tracksartist-title-slugyml), the format that
`nextrack_lights.py` renders, compiles and applies. This file is the manual for the agents that
write shows. Everything the compiler needs is in YAML; logic lives in two Python registries,
[gestures](#gestures) (effects in time) and [rules](#show-rules) (budgets and bans).

```
anchors on the musical map  ->  cues  ->  looks / gestures  ->  sections  ->  lightshows/tracks/<slug>.yml
```

If you have just arrived, run `uv run scripts/nextrack_show.py vocab [<show-id>]`. It prints the
anchor grammar, each layer's words and mapping keys, every gesture and rule with its
parameters, and the show's palette and looks, always in step with the code.

## The loop

1. **Read the music.** `uv run scripts/nextrack_map.py show "<Artist — Title>"` gives the
   sections, the drops and the owner's hot cues. A track needs its
   [musical map](../README.md#musical-maps) (`lightshows/maps/<slug>.yml`) first; a map that
   fails its `musical-map` check counts as none, and the finding says
   `lightshows/maps/<slug>.yml is not a valid map: fix its musical-map finding`. `show`
   draws the sections as a strip of letters, one per bar; to write `<kind>.<i>` anchors, read
   the numbered list instead: `grep -E '^(bars|hot_cues|sections):' lightshows/maps/<slug>.yml`
   prints the bar count, the hot cues and the sections in order, and `break.3` is the third
   entry with `kind: break`.
2. **Edit the show:** `show.yml` (the night) or one track file (its cues).
3. **Build:** `uv run scripts/nextrack_show.py build <show-id>`. Findings come as
   `path:line: rule-id: message` and name the value and the fix.
4. **Read the night:** `uv run scripts/nextrack_show.py report <show-id>`: every section, what
   produced it, the music under it, the budget tally. Critique it as a whole.
5. **See a track:** `uv run scripts/nextrack_lights.py render "<Artist — Title>" --choreo lightshows/tracks/<slug>.yml -o <scratch>/sim.html`
   (needs the SoundSwitch project; the language does not).
6. Repeat from 2. **Never edit `lightshows/tracks/<slug>.yml` of a show**: it starts with the
   header `# Generated by scripts/nextrack_show.py build from ...` and the next build
   overwrites it. Writing into SoundSwitch (`apply`) stays the owner's call.

`check_repo.py` runs the same compile (`show-source`, `show-rules`, `show-compiled`), so a show
that is not built, or whose rules fail, never gets merged. `build` writes the files even when
only rules fail, so a draft can be rendered and critiqued; it then exits 1.

**Variants.** To try an alternative without touching the committed show, copy the folder
outside the repo, change it, and build with `--out`:

```bash
cp -r lightshows/shows/<show-id> <scratch>/variant
uv run scripts/nextrack_show.py build <scratch>/variant --out <scratch>/out
uv run scripts/nextrack_lights.py render "<Artist — Title>" --choreo <scratch>/out/<slug>.yml -o <scratch>/sim.html
```

`--out` writes the choreographies into that folder with no ownership check. A show folder
outside `lightshows/shows/` builds only with `--out`.

## The folder

```
lightshows/shows/<show-id>/
  show.yml                                   # the night
  <slug>.yml                                 # one cue list per track, named like its map
```

`<show-id>` is a kebab-case id, normally the stem of the light plan
(`lightshows/sets/<show-id>.md`). A track file is named `<slug>.yml`, where the slug is the stem
of the track's map (`lightshows/maps/<slug>.yml`), which is also the stem of the choreography
it generates. A wrong name is a finding that says the right one. The tracks of the show are
the tracks of the set (`set:` in `show.yml`: each block its program links, in order, and each
line of the block's `## Tracklist`). Every set track needs exactly one track file; a file for a
track that is not in the set is a finding; a track played twice in the set is a finding (a track
has one choreography). Order is never written in the show.

Names are kebab-case ids: lowercase letters and digits joined by single `-` (palette entries,
looks, cues, moments, shows). Prose (`story`, `intent`, `budget`) is pt-BR. Ids, keys and
values are English or pt-BR words as the owner's show uses them (`respiracao`, `breu`).

YAML gotchas: an unquoted `off`/`on` is read as a boolean. A layer written `off`/`on` is fine
(the compiler gives the words back), and booleans inside a layer mapping (`mirror: true`) stay
booleans. Write `1/4` without quotes (it is a string); quote anything starting with `#`, `&`
or `*` (`track: '&ME, Black Coffee — The Rapture Pt.III'`: unquoted, `&ME` is a YAML anchor
and the file does not parse). Inside single quotes an apostrophe is doubled (`'Can''t'`).

## `show.yml`

This example is the one the repo's tests compile (two tracks, a bridge and a handover):

```yaml
show_version: 1
set: sets/teste.md
story: 'Uma noite de teste: o azul abre, o vermelho fecha.'
palette:
  azul: '#0A2CFF'
  vermelho: '#FF0A2A'
  violeta: '#6A1CFF'
looks:
  respiracao:
    movers: {move: sweep, every: 2bar, positions: [Dance Floor Centre, Crossed Over], colour: azul, level: 0.7}
    matrix: {draw: rows-up, rate: 1bar, colour: azul, mirror: true}
    hue: {state: pulse, colour: vermelho}
  pulso:
    extends: respiracao
    movers: {move: blink, every: 1/4, colour: vermelho, positions: null, position: Crossed Over}
    matrix: {draw: centre-out, rate: 1/8, colour: vermelho}
  breu: {movers: off, matrix: off, hue: dark}
gesture_defaults:
  spiral:
    rates: [1/2, 1/4]
    colours: [azul, violeta]
    aims: [[Crossed Over, Up], Dance Floor Centre]
bridge:
  name: ponte
  intent: 'Ponte: a mesma luz da música anterior, até a chegada.'
handover:
  name: entrega
  intent: 'Entrega: do G até o fim, o look que a próxima copia.'
```

| key | |
|---|---|
| `show_version` | required: `1` |
| `set` | required: repo-relative path of the set (`sets/<set>.md`); the track order comes from it. An absolute path or one with a `..` part is a finding |
| `story` | required, pt-BR: the idea of the night |
| `palette` | required: name -> `#RRGGBB`. A `colour` in movers, matrix and hue may be a palette name |
| `plan` | optional: repo-relative path of the prose light plan (`lightshows/sets/<show-id>.md`), with the same check as `set` |
| `looks` | optional: name -> [look](#looks) |
| `gesture_defaults` | optional: gesture name -> parameters merged under every call of that gesture (the cue's `with` wins; `null` removes a default). Its problems land in `show.yml`: see [Gestures](#gestures) |
| `bridge` | optional: `{name, intent, bars?}`, `name` and `intent` required when `bridge` is present. Without it no bridges are made. `bars` (1-32) is the mix window: see [The handover and the bridge](#the-handover-and-the-bridge) |
| `handover` | optional: `{name, intent}`, both required when `handover` is present. The default `name`/`intent` of the handover sections of the track files; needed when a track's handover does not write its own |
| `rules` | optional: rule id -> parameters (or `true`). Chooses which [rules](#show-rules) run; none written, none run |
| `advice` | optional: rule id -> parameters, as in `rules` (a rule may be in both, with other parameters). Design goals: their findings (`show-advice`) are printed by `build` and `report`, and never fail `check_repo.py` or change an exit status |

## A track file

```yaml
track: Pedro Sampaio — Dançarina
story: 'Dançarina abre a noite: o azul respira, a espiral gira e a virada acende o vermelho.'
cues:
  - at: drop.1
    name: chegada
    role: arrival
    intent: 'A chegada: o azul respira.'
    look: respiracao
  - at: break.1
    name: espiral
    intent: 'Espiral: os lados revezam cada vez mais rápido.'
    gesture: spiral
    with: {bars: [2, 2]}
  - at: drop.2
    name: virada
    moment: virada
    accents: [white, strobe]
    intent: 'A virada: tudo em vermelho.'
    look:
      movers: {move: blink, every: 1/4, colour: vermelho, position: Crossed Over}
      matrix: {draw: solid, rate: 1/8, colour: vermelho}
      hue: {state: pulse, colour: vermelho}
handover:
  look: pulso
  moment: passagem
  accents: [white]
```

```yaml
track: Chiclete com Banana — Voa Voa (Ao Vivo)
story: Voa Voa recebe a ponte e fecha a noite com o rolo de estrobo.
budget: Um rolo de estrobo no último drop.
cues:
  - at: drop.1
    name: chegada
    role: arrival
    look: pulso
    with: {matrix: {draw: zigzag}}
  - at: break.1
    name: subida
    look: respiracao
    with:
      movers: {move: pingpong, every: 1/2, faster_from: 'drop.2 - 2', faster_every: 1/4, positions: null, position: Up, level: null}
  - at: drop.2
    name: final
    moment: final
    accents: [strobe-roll]
    look: pulso
```

Keys: `track`, `story` and `cues` (a list, possibly empty) are required; `budget` (pt-BR prose),
`handover` and `bridge` (only `false`: no bridge into this track) are optional.

**`track` is written exactly as the map's `track`** (`Artist — Title`, with the em dash). The
compiler finds the map by the same matcher the blocks use and says so when the text differs.

### Cues

A cue starts at an anchor and lasts until the next cue (a cue stack: no overlaps).

| key | value |
|---|---|
| `at` | required: an [anchor](#anchors), the cue's first bar |
| `until` | optional: an anchor, the first bar **after** the cue (exclusive); leaves a gap that stays on the autoscript |
| `name` | required: kebab-case; becomes the section name (a gesture derives its sections' names from it). May repeat in a track (`drop`, `corte`) |
| `intent` | optional pt-BR prose, copied to every section the cue makes (each step of a gesture) |
| `look` | a look name, or a mapping of layers. Exactly one of `look` and `gesture` |
| `gesture` | a [gesture](#gestures) name |
| `with` | optional. With `look`: layer overrides (see [Looks](#looks)). With `gesture`: its parameters |
| `role` | optional: `arrival`, the drop that shows the new track. Only the cue's first section carries it |
| `moment` | optional: a kebab-case moment name, as the light plan names its moments; the `budget` and `matrix-not-cloned` rules read it. Every section of the cue gets it |
| `accents` | optional list: `white` (one beat of the white strip on the cue's first beat), `strobe` (a strobe hit there), `strobe-roll` (a strobe roll over the cue's first section) |

Spans: a cue runs from `at` to the bar before the next cue's `at`, or to `until - 1` when it has
`until`. The last cue runs to the bar before the handover, or, with no handover, to the map's
last bar (the report lists each default end under "decided by the compiler"). `at` must
increase strictly. `until` must be after `at` and no later than the next start. Every cue
covers at least one bar. Accents go on the first section of the cue; an accent whose layer the
look already sets on that section is a finding (remove one of the two).

### The handover and the bridge

The **handover** is the look that plays from G to the end of a track and that the next track's
bridge copies. In the track file:

```yaml
handover:
  look: pulso              # a look name or a mapping of layers (required)
  with: {...}              # optional overrides
  at: G                    # optional anchor, default G
  until: end + 1           # optional anchor, default: after the map's last bar (with bridge.bars: at + bars)
  name: entrega            # optional, default: the show's handover.name
  intent: "..."            # optional, default: the show's handover.intent
  moment: passagem         # optional
  accents: [white]         # optional; accents stay on this track, the bridge ignores them
```

Unlike `show.yml`, where `name` and `intent` are both required, a track file's handover may omit
them and inherits the show's; with neither, it is a finding.

The **bridge** is made by the compiler, never written. When the show has `bridge`, the track is
not the first in the set, the track before it has a handover, the map has a hot cue `B`, and
the track file does not say `bridge: false`, the track opens with a section from `B` to the bar
before its first cue (or its handover, or the map's end), named and described by the show's
`bridge`, with exactly the layers of the previous handover (after merging and palette
resolution, without accents). The continuity of the night is that copy.

**`bridge.bars`** (optional, 1-32) is the length of the mix window, on both sides. The handover
runs by default from its start (`G`, or its `at`) for `bars` bars, not to the map's end, and an
explicit `until` past that is a finding at the handover. The bridge still runs from `B` to the
bar before the first cue, and a first cue (or handover) after `B + bars` is a finding there:
`the bridge ends at bar <B + bars - 1> (bridge.bars <n>); start a cue at or before bar <B + bars>`.
Without `bars`, nothing changes. The [`bridges`](#show-rules) rule measures the windows.

Consequences, each a finding that says what to do:

- A track whose map has a `G` followed by a track that would take a bridge needs a handover.
- The next track needs a hot cue `B` (add it in rekordbox and run `nextrack_map.py cues`), or
  `bridge: false`.
- The next track's first cue (or handover) must start after `B`.
- A bar number in the outgoing track means nothing in the incoming one. A handover whose layers
  hold one (`movers.faster_from`, or a raw `white.accent`, `strobe.hit`, `strobe.roll`) is a
  finding **at the handover** when a bridge would copy it. Move the effect to a cue before the
  handover, or write `bridge: false` in the next track. (`accents:` are not copied, so they are
  fine.)

## Anchors

Time is anchored on the musical map; never count bars by hand.

```
anchor := term [ ("+" | "-") n ]
term   := n                  an absolute bar (from 1)
        | A … H              the bar of that hot cue in the map (`hot_cues`)
        | <kind>.<i>         the first bar of the i-th section of that kind (from 1)
        | <kind>.<i>.end     its last bar
        | end                the map's last bar
kind   := intro | groove | break | build | drop | outro
```

An anchor is a YAML integer (`16`) or a string (`drop.2 - 1`, `G`, `break.1.end + 1`; spaces
around the sign are optional). `drop.i` is the i-th section of kind `drop` (the same bar as
the i-th entry of the map's `drops`, whose `db` the report shows). A hot cue that is not on a
bar's first beat (`9.3`) cannot be an anchor. Every failure names what the map has, such as
`drop.4: the map has 2 drop sections (9, 21)` or `G: the map has no hot cue G (it has A, B)`.
A resolved bar must be inside `1 ... bars`, except for an `until`, which may also be
`bars + 1` (`end + 1`: the cue runs to the last bar). Note that `end` is the last bar itself, so
`until: end` leaves the last bar out.

`movers.faster_from` takes an anchor too. Every other bar in a layer (the raw `white.accent`,
`strobe.hit`, `strobe.roll`, written `"<bar>.<beat>"` or `[a, b]`) stays absolute, an escape
hatch; prefer `accents:`.

## Layers

A layer value is exactly the choreography vocabulary of
[lightshows/README.md](../README.md#layers): `movers`, `matrix`, `white`, `uv`, `strobe`, `hue`,
each `auto`, `off` or a mapping. `vocab` lists each layer's words and keys, the moves, draws,
hue states and rates. Three differences in a show:

- a `colour` (movers, matrix, hue) may be a palette name; `#RRGGBB` is still accepted;
- `faster_from` may be an anchor;
- a key set to `null` in a `with` override removes it (`with: {movers: {positions: null, position: Up}}`).

A layer the look does not name stays `auto` (the autoscript). `haze` is not a layer: every
compile holds it. The compiler validates its output with the choreography's own checker; a
problem there (an unknown draw, a bad rate) is a `show-source` finding at the cue that produced
it, so you never need to read the generated file to find an error.

## Looks

A look is a mapping of layers with an optional `extends: <look>`. Merging is per layer. When
the base value and the override are both mappings their keys merge (the override wins, `null`
removes a key); otherwise the override replaces the base value, and `null` removes the layer.
A cue's `look: name` plus `with:` is the same merge applied on top. In the example, `pulso`
extends `respiracao`, replaces the movers' keys and the matrix draw, and keeps `hue` and
`matrix.mirror`. An unknown look (the message lists the defined ones and a close match), a
cycle of `extends` or a layer name outside the vocabulary is a finding. A look that is not used
anywhere is fine. Do not name a look like a gesture or an effect key (`spiral`, `strobe`...).

## Gestures

A gesture is a Python function in [`scripts/show_gestures.py`](../../scripts/show_gestures.py)
that fills the bars of one cue with sections. A cue invokes it with `gesture: <name>` and its
parameters in `with`; the show's `gesture_defaults` are merged underneath. The sections it
returns are named from the cue (`<cue name>-...`) and cover exactly the cue's span; bad
parameters are `show-source` findings at the cue, with the fix in the message.

A problem in `gesture_defaults` lands in `show.yml`, where the fix goes. A key the gesture does
not take is a finding there (with a close match), even for a gesture no cue calls. A bad value
that a cue takes from the defaults, because its own `with` does not set that parameter (a rate,
a palette name), is reported once at `show.yml`, ending `(from gesture_defaults.<gesture> in
show.yml)`, not in every track file that calls the gesture. A cue that sets the parameter
itself does not see the default's problem. A problem that depends on the cue (the bars do not
add up to its span) stays at the cue.

| gesture | parameters | what it does |
|---|---|---|
| `sequence` | `steps`: a list of `{bars, look, with?, name?}` | One section per step, consecutive; the bars add up to the cue's span. `look` is a look name or a mapping of layers, `with` is merged on top. A step's name defaults to `<cue name>-<i>` counted from 1. A step with `look: <name>` reports that look for the budget. The way to compose an effect in time from looks, with no new code |
| `spiral` | `bars`, `rates`, `colours`, `aims`: four lists of the same length, one entry per step | The v1 spiral, the relay that speeds up: the two sides take turns, faster step by step, centre dark. Per step: movers `pingpong` every `<rate>` in `<colour>` aimed at `<aim>`, matrix `columns` at `<rate>` with `pingpong`, hue `dark`. Rates are `1/16`, `1/8`, `1/4`, `1/2` or `<n>bar`. An aim is a preset name (`position`) or a list of them (`positions`). Bars add up to the span. Sections are named `<cue name>-<rate>` with the slash as a dash (`espiral-1-4`) |

A `sequence` cue, valid on the example above (a 4-bar span):

```yaml
- at: drop.2
  name: quebra
  gesture: sequence
  with:
    steps:
      - {bars: 2, look: respiracao}
      - {bars: 2, look: pulso, name: volta}
```

Adding a gesture is a code change with a test: see the checklist in
[CLAUDE.md](../../CLAUDE.md#change-checklists). Until then, compose with `sequence`.

## Show rules

A rule is a Python function in [`scripts/show_rules.py`](../../scripts/show_rules.py), chosen
and parameterised under `rules:` in `show.yml`. It reads the compiled show and returns
`show-rules` findings that point at the cue (or handover) to fix, in the file of the agent that
owns it. Bad parameters, or a rule id that is not registered, are `show-source` findings at
`rules:`. Rules run only when the show compiles.

```yaml
rules:
  budget:
    pulso: {max: 1}
    strobe: {max: 5, moments: [virada, final], from: "Pedro Sampaio — Dançarina"}
  total-dark: {only: [breu]}
  arrivals: {draw_differs: true}
  movers-aim: true
  matrix-not-cloned: {except_moments: [virada, final]}
  exclusive: {keys: [spiral, pulso], except_tracks: ["Pedro Sampaio — Dançarina"]}
```

| rule | parameters | finding when |
|---|---|---|
| `budget` | key -> `{max?, moments?, from?}`. A key is a look name, a gesture name, `white-accent`, `white-flash`, `strobe` or `uv` | a key has more than `max` occurrences (one finding at the first one past the max; the message lists them all, track and bar); an occurrence whose cue has no `moment` in `moments`; an occurrence in a track before `from` (the `Artist — Title` of a show track) in set order. An unknown key is a parameter problem |
| `total-dark` | `{only: [look or gesture names]}` | a compiled section (a bridge too) with movers `off`, matrix `off`, hue `dark` or `off` (or `{state: dark}`), and white, strobe and uv each unwritten, `auto` or `off`, has neither its look nor its gesture in `only` |
| `arrivals` | `true` or `{draw_differs?: bool}` | a track has no cue with `role: arrival`, or more than one; with `draw_differs`, two consecutive tracks' arrival sections have the same matrix draw |
| `movers-aim` | `true` | a compiled section's movers is a mapping without `position` or `positions` (the autoscript would pick a random preset every two bars) |
| `matrix-not-cloned` | `true` or `{except_moments?: [names]}` | a compiled section's matrix is a mapping with neither `mirror` nor `pingpong` (both Vorlanes would draw the same), and its cue's moment is not excepted |
| `exclusive` | `{keys: [two or more budget keys], except_tracks?: [Artist — Title, or the title]}` | a track has occurrences of more than one of `keys` |
| `bridges` | `{max: 1-32}` | a compiled handover section, or the bridge section that copies it, is longer than `max` bars. Both findings point at the handover's line in the outgoing track's file (the handover owns the window) and name both lengths and both tracks |

A show with no `rules` runs none. Under `advice:` the same rules are design goals: their
findings carry the rule id `show-advice` and never fail a check (an unknown id or a bad
parameter there is still a `show-source` finding, prefixed `advice.<id>:`). Adding a rule is a code change with tests: see
[CLAUDE.md](../../CLAUDE.md#change-checklists), whose last step is the row in this table.

### Provenance and occurrences

The rules count **occurrences**, from the compiled sections, each with its provenance:

- `kind`: `cue`, `bridge` or `handover`; `track`: the track whose choreography holds it;
- `look`: the name of the look that produced the section (the `look: <name>` of a cue or a
  handover, or the one a gesture step reports); empty for inline layers. `gesture`: for the
  sections a gesture made;
- `role` and `moment`: those of the cue, given to every section it produced (`role: arrival`
  marks only the first section);
- `path` and `line`: where a finding about this section points.

Provenance is per section, so a `sequence` step with `look: breu` counts as `breu`. A **bridge**
section takes the record of the handover it copies, in the outgoing track's file, so a finding
about a bridge lands in the file of the agent who owns the handover, which is where the fix
goes; a moment exception applies to the copy as it does to the original.

| key | an occurrence is |
|---|---|
| a look name | a compiled section (not a bridge) whose look is that name: a cue or handover with `look: <name>`, or a gesture step that reports it (only the name used, not the looks it extends) |
| a gesture name | a cue that invokes it |
| `white-accent` | one beat of a `white.accent` list in a compiled section |
| `white-flash` | a compiled section with `white: {flash: ...}` |
| `strobe` | one beat of `strobe.hit`, or one `strobe.roll` |
| `uv` | a compiled section with `uv: on` or `movers.move: uv` |

Bridges never count: they copy a look already counted where it was written. An `accents` entry
produces a `white-accent` or `strobe` occurrence like the raw form does.

## Reading `build` and `report`

`build` prints `wrote <path>` or `unchanged <path>` per choreography, then a
`stale <path>: owned by this show, which no longer compiles it; delete it` line per
choreography that has this show's header but whose track the show no longer compiles (a track
that left the set: `build` never deletes it, and exits 1 until you do), then the findings and
`N finding(s)`, then the advice (`show-advice` lines) and `N advice`, which never change the exit
status. With any `show-source` finding it writes nothing. The compiler stops a track at the first step
that finds something (anchors, then spans, looks and gestures, accents, colours), so fix the
findings you see and build again: later ones may appear. Exit status: `0` clean, `1` findings, `2` usage. `report` prints the night and exits 1
when it printed any finding. The report from the example above (shortened):

```
1. Pedro Sampaio — Dançarina · 32 bars · B 5 · G 25
  9-16 chegada | look respiracao | movers sweep every=2bar ... | arrival | music: drop 9-16, drop +12.5 dB
  17-18 espiral-1-2 | gesture spiral | movers pingpong every=1/2 colour=azul positions=[Crossed Over, Up]; ... | music: break 17-18
  21-24 virada | look (inline) | ...; white accent=[21.1]; strobe hit=[21.1]; ... | moment virada | music: drop 21-24, drop +12.5 dB
  25-32 entrega | handover pulso | ... | moment passagem | music: drop 25-32
2. Chiclete com Banana — Voa Voa (Ao Vivo) · 32 bars · B 5 · G 25
  5-8 ponte | bridge pulso | ... | moment passagem | music: intro 5-8
  ...
budget

arrivals
```

## Who owns a choreography

`build` writes `lightshows/tracks/<slug>.yml` with a two-line header naming the show. The rules
of ownership:

- `build` overwrites a choreography that has the header of this show.
- A hand-written file (no header) is refused: `refused <path>: not generated by a show; use --adopt to take it over`.
  `--adopt` takes over only hand-written files (the first build of a ported set).
- A file owned by another show is always refused. The conflict is resolved in the shows, not
  by a flag; the validator also reports a track owned by two shows.
- With any refusal, nothing is written.
- `build --check` writes nothing and prints `would change <path>` per file that differs; exit
  1 if any does.
- `build` and `build --check` print `stale <path>: owned by this show, which no longer compiles
  it; delete it` for a file with this show's header whose track the show no longer compiles.
  Neither deletes it; both exit 1 until it is gone.
- `build --out DIR` writes elsewhere with no ownership check (variants, above).

The emitted text is deterministic (layers in a fixed order and key order, flow style), so the
same show gives the same bytes. `show-compiled` fails when a committed choreography is missing
or differs from what its show compiles to; the message says to run `build <id>`, or, for a
hand-written file, `build <id> --adopt` to take it over.

**Porting hand-written choreographies.** Copy the stories, budgets and intents verbatim, build
with `--out <scratch>/out` first and compare each generated file with today's one, parsed
(`yaml.safe_load`; the emitted file quotes `"off"`, so read a top-level `False` as `off`): the
header and the formatting change, the data must not. Only then run `build <id> --adopt`, once.

## Writing a show, start to finish

1. Pick the set (`sets/<set>.md`) and make sure every track has a map. `nextrack_map.py show`
   each track; note its drops, breaks, and hot cues `B` and `G` (the numbered sections: see
   [the loop](#the-loop), step 1).
2. Write `show.yml`: `story`, `palette`, a few `looks`, `bridge` and `handover` (if the night
   flows through bridges), and `rules` last.
3. Write one track file per track, named `<map slug>.yml`, `track` copied from the map. Start
   with the arrival (`role: arrival`) and the handover; add cues with anchors where the music
   names the bar (a section start, a hot cue, `drop.2 - 1` for the bar before a drop). A bar
   number is for a cue the light places inside a section.
4. `build`. Fix findings from the top. Then `report`, and critique the whole night: budgets,
   arrivals, what repeats.
5. `render` the tracks that matter; iterate.
6. `uv run scripts/check_repo.py` and `uv run pytest` before calling it done.
