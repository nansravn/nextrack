# lightshows/ — the rig, shows, per-track choreographies and show plans

The room's lights are driven by SoundSwitch, which writes an automatic script for every
track (the *autoscript*). This folder holds what makes that script yours:

| path | what it is |
|---|---|
| `rig.yml` | the room and its fixtures, by SoundSwitch node name |
| `tracks/<artist-title-slug>.yml` | the **choreography** of one track: sections of bars, each saying what a layer does |
| `sets/<set-file-stem>.md` | the **show plan** of a set: its story, palette per block and the effect budget |
| `shows/<show-id>/` | a **show**: one night written in the show language (`show.yml` plus one cue list per track), compiled into the choreographies above; see [shows/README.md](shows/README.md) |
| `maps/<artist-title-slug>.yml` | the **musical map** of one track: what the music does, bar by bar (generated, see [Musical maps](#musical-maps)) |

A track without a choreography keeps the autoscript. A choreography replaces only what it
names; everything else (an unset layer is `auto`) stays as SoundSwitch wrote it. What the
autoscript does on its own is in
[docs/soundswitch/autoscript-analysis.md](../docs/soundswitch/autoscript-analysis.md); the
rig is in [docs/rig.md](../docs/rig.md#lights-and-room); the file format in
[docs/soundswitch/file-format.md](../docs/soundswitch/file-format.md).

Prose in the files (`story`, `intent`, plan text) is pt-BR; keys and values are English.

## Workflow

1. **Write the choreography** (by hand, or with the agent skill for it) from the track's
   structure (its [musical map](#musical-maps), when it has one) and the show plan's budget.
   For a set written as a [show](shows/README.md), write the show's track file instead and
   run `uv run scripts/nextrack_show.py build <show-id>`: it generates the choreography.
2. **See it:** `uv run scripts/nextrack_lights.py render "<track>" --choreo lightshows/tracks/<slug>.yml -o /tmp/sim.html`
   writes the room simulator, before and after, on a timeline (add the audio file in the
   page to hear it). Nothing is written to SoundSwitch.
3. **Compile** to a file: `compile lightshows/tracks/<slug>.yml -o out.ssfile`. Use it to
   inspect; the project is untouched.
4. **Apply** with SoundSwitch closed: `apply lightshows/tracks/<slug>.yml` is a dry run
   that prints what would change, then `--apply` writes it (backup first).
   [scripts/README.md](../scripts/README.md#nextrack_lightspy) has the safety model.
5. Open SoundSwitch, play the bars, add the **manual cues** the tool printed, and run
   `uv run scripts/check_repo.py`. Then run `status` (or `status --block <block-id>`) to see
   whether the track is compliant; edits made in SoundSwitch after an apply are settled with
   `restore` or `accept` (see
   [scripts/README.md](../scripts/README.md#compliance-status)).

## `rig.yml`

```yaml
room: {shape: rectangle, front: N}
fixtures:
  mover-ne:  {node: "Mover 1", corner: NE, kind: mover}
  matrix-nw: {node: "VORLANE VL-1000 RGBW v2", index: 1, corner: NW, kind: matrix, aim: centre}
  haze:      {node: " Lig Light LL-HZ600K", kind: haze, level: 0.5, fan: "Main -  Lig Light LL-HZ600K", fog: "..."}
  hue:       {kind: hue-chandelier, corner: centre, lamps: 7, follows: main-track}
matrix:
  rows: [colour, colour, colour, white, colour, colour, colour]   # 8 zones per row
  zone_order: row-major-top-left
  white_max: 0.6        # ceiling of the white strip, 0-1
```

Keys: `room` (`shape`, `front` in `N E S W`), `fixtures`, `matrix`. A fixture is
`{kind, node, index, corner, aim, fan, fog, lamps, follows, level}`: `kind` is `mover`,
`matrix`, `haze` or `hue-chandelier`; `node` is the SoundSwitch node **name** (required
unless `hue-chandelier`; ids are looked up in the venue, they change between rigs);
`index` picks the n-th node with that name (the two Vorlanes share one); `corner` is `NE`,
`SE`, `NW`, `SW` or `centre`. `matrix` is `{rows, zone_order, white_max}`: `rows` lists
`colour` / `white`, `white_max` is a number in (0, 1]. The haze fixture's `level` (0-1]
holds fan and fog over the whole of every compiled track.

## Choreography: `tracks/<artist-title-slug>.yml`

```yaml
track: Marshmello x Bastille — Happier      # must match a pool track
soundswitch: F41EB9E9-B82B-4F58-A40C-B039222EBB0E   # the script GUID (nextrack_lights.py tracks)
grid: {bpm: 100, downbeat: "0:00.158"}      # checked against the script's tempo map
story: >-                                    # prose: what the light says about the song
budget: >-                                   # optional: what this track spends
base: autoscript
sections:
  - bars: [21, 28]            # inclusive, from 1, sorted, no overlap
    name: subida-1
    intent: ...               # optional
    movers: {move: pingpong, every: 1bar, colour: "#00C8FF", faster_from: 27, faster_every: 1/2}
    matrix: {draw: fill-up, rate: 1bar, mirror: true}
    hue: dark
```

A choreography whose first line is `# Generated by scripts/nextrack_show.py build from ...`
comes from a [show](shows/README.md) and is never edited by hand: change the show's track file
and run `uv run scripts/nextrack_show.py build <show-id>`; `show-compiled` fails when the file
drifts. A choreography without the header is hand-written and edited as described here.

Keys: `track` (`Artist — Title`), `soundswitch` (GUID), `grid` (`{bpm, downbeat}`), `story`,
`budget` (optional), `base` (`autoscript`), `sections` (may be empty: see [Haze](#haze)).
A section is `{bars: [a, b], name, intent?}` plus any of the layers. Bars are counted from
the downbeat in `grid`; the compiler maps them through the script's tempo map and refuses
a track with more than 8 tempo anchors. YAML reads an unquoted `off` / `on` as a boolean;
both spellings are accepted.

### Layers

A layer is `auto`, `off` or a mapping.

| layer | values |
|---|---|
| `movers` | `{move: hold\|pingpong\|sweep\|blink\|uv, every, colour, level (0-1], position, positions, faster_from (bar), faster_every}` |
| `matrix` | `{draw: solid\|rows-down\|rows-up\|columns\|zigzag\|centre-out\|arrow-up\|fill-up, rate, colour, mirror, pingpong, with_white}` |
| `white` | `{accent: ["<bar>.<beat>", ...]}` or `{flash: <rate>}` |
| `uv` | `on`, `off`, `auto` |
| `strobe` | `{hit: ["<bar>.<beat>", ...]}` or `{roll: [a, b]}` |
| `hue` | `dark`, `pulse`, `bright`, or `{state: dark\|pulse\|bright, colour}` |

Rates are `1/16`, `1/8`, `1/4`, `1/2` or `<n>bar` (a bar is four beats); colours are
`#RRGGBB`.

- `movers`: `hold` and `sweep` stay lit at `level` (default 0.85; the position, not the
  light, moves); `pingpong` lights one mover per step, the other dark, `every` long (default
  `1/4`); `blink` pulses every step; `uv` is a manual cue. `position` / `positions` are
  venue preset names (`DJ Booth`, `Dance Floor Centre`, `Up`, ...); several are cycled,
  one per step. `faster_from` is an **absolute bar** from which `faster_every` replaces
  `every`.
- `hue`: the Hue chandelier follows the Main track, so this layer edits Main. `dark` is
  0, `bright` steady 0.85, `pulse` one pulse per beat. `off` means `dark`.
- `white`: the white strip never goes above the rig's `white_max`. `accent` is one beat at
  each `bar.beat`; `flash` pulses at the rate.
- `strobe`: v1 is 1/16-note pulses on the movers and the colour cells for one beat per
  `hit`, or for the bars of `roll`.

### Haze

Haze is a constant thin mist, not a layer: `haze` in a section or in a show plan's
`budget` is a finding.
Every compiled track holds the haze fixture's fan and fog at the rig's `level` over the
whole track, from 0 ms to the end (the script's last event, or the song when it is
longer), before, inside and after the sections. Whatever the autoscript had on the two
channels (they follow Main) is replaced. Until the machine is confirmed to react, every
compile prints one experimental manual cue for it.

A choreography may have `sections: []`: the autoscript everywhere, plus the haze. Without
sections no bar number is used, so `grid` is not checked against the script and a track
with more than 8 tempo anchors compiles too.

### The matrix draws

The two Vorlanes are 8 columns by 7 rows of cells (see [the rig](../docs/rig.md#lights-and-room)).
Rows 0-2 and 4-6 are colour, row 3 is the white strip, lit only by `with_white`. One step
of the draw is one `rate`; `k` is the step (from 0), `#` is a lit cell. One frame of each
draw, rows top to bottom:

```
solid          rows-down k=1   rows-up k=0     columns k=2     fill-up k=2
########       ........        ........        ..#.....        ........
########       ########        ........        ..#.....        ........
########       ........        ........        ..#.....        ........
........       ........        ........        ........        ........
########       ........        ........        ..#.....        ########
########       ........        ........        ..#.....        ########
########       ........        ########        ..#.....        ########

centre-out q=0 centre-out q=1  zigzag k=2      zigzag k=9      arrow-up k=3
...##...       ..#..#..        ..#.....        ........        ........
...##...       ..#..#..        ........        ......#.        ........
...##...       ..#..#..        ........        ........        ...##...
........       ........        ........        ........        ........
...##...       ..#..#..        ........        ........        ..#..#..
...##...       ..#..#..        ........        ........        .#....#.
...##...       ..#..#..        ........        ........        #......#
```

- `solid`: every colour cell, every step (a pulse per step, not steady light).
- `rows-down` / `rows-up`: one row per step, top to bottom or the reverse, wrapping.
- `fill-up`: from the bottom, one more row per step; once full, every row keeps pulsing
  each step.
- `columns`: one column of every colour row per step, left to right, wrapping.
- `centre-out`: two columns from the middle (3 and 4), then 2 and 5, and so on, wrapping every four steps.
- `zigzag`: one cell per step, snake order: row 0 left to right, row 1 right to left, ...
- `arrow-up`: a "^" whose apex rises one row per step; cells past the bottom row are cut.

Options of `matrix`: `colour` (default depends on the draw), `rate` (default `1/4`),
`mirror` (the second Vorlane draws flipped, so the two bars are symmetrical across the
room), `pingpong` (the first Vorlane gets the even steps and the second the odd ones),
`with_white` (the white row takes part in the draw, at `white_max`).

## What the compiler does that matters to an author

- **Unset is `auto`.** A layer you do not write stays as the autoscript wrote it. A
  fixture the rig names but the venue or the script lacks is skipped with a manual cue.
- **White is off under a drawing.** With `matrix` other than `auto`, an unset `white` is
  `off`, because the autoscript's white strip washes colour out. A draw with
  `with_white: true` lights the strip itself, so there `white` stays `auto`. To ask for
  white in a section with `matrix: auto`, write it.
- **The Main track is the Hue centre.** `hue` rewrites Main for the section. Fixtures
  that follow Main there would change too, so the compiler first copies the old Main onto
  every fixture track that is not edited by this section for the lanes `hue` changes;
  a `hue` layer therefore does not alter movers or Vorlanes by side effect. Only leaf
  nodes get the copy: group nodes (a Vorlane, the haze, "Group 4") carry no content.
  A `hue` colour cuts Main's colour blocks, most of them gradients; what is left of a cut
  gradient keeps showing the colours it showed.
- **Pulses.** Every draw is a per-step sawtooth: each lit cell jumps to full at the step
  and decays to dark over that one step, like the autoscript. That holds for `solid` and
  for the full rows of `fill-up` too: they pulse every step, they are not steady light.
  A Vorlane's master is held at full under a draw.
- **Positions.** A mover section that names a `position` or `positions` replaces the
  autoscript's position flags inside it and removes, whole, every autoscript shape block
  (movement) that overlaps it; a mover section without a position keeps the autoscript's
  positions and movement, which change preset every two bars. When the autoscript's position
  block goes on past the section, the preset it had in force there comes back at the first
  moment after the section.
- **Manual cues.** What the compiler cannot write is printed as `manual cue, bar N: ...`
  by `render`, `compile` and `apply`: `uv`, `move: uv`, the whole-track haze (one per
  compile, to confirm the machine reacts; or why it was skipped), a position preset the
  venue or script does not have, a shape block cut by a position change where the removed
  part would have shown (not where another section keeps the movers dark or aims each mover
  at a preset in its palette), a strobe `off` over SoundSwitch's own strobe blocks. Add these
  in SoundSwitch by hand.
- **Nothing outside the sections changes.** `apply` refuses unless everything outside the
  rig's tracks and Main equals the base, and outside the sections every venue track and
  Main shows the base's intensity, colour and position. The one exception is the haze
  fixture's fan and fog: outside the sections they change only to the rig's `level` over
  the whole track.
- **Undo.** To return a track to the autoscript, close SoundSwitch and copy
  `nextrack-backups/base/{GUID}.ssfile` (next to the project folder) over the file of the
  same name in the project folder. To undo only the last `apply`, use the `restore:` line
  it printed. [scripts/README.md](../scripts/README.md#safety-model-of-apply---apply) has
  what the next `apply` then asks for.

## Show plan: `sets/<set-file-stem>.md`

```markdown
---
set: sets/2026-10-31-halloween-em-casa.md     # the set, relative to the REPO ROOT
budget:                                       # where each rare effect may appear
  white-accent: [peak-1, peak-2]
  strobe: [peak-2]
  uv: [halloween-chegada]
---
# Plano de luz — ...
```

`set` is the path of the set file, **relative to the repo root** (not to this file).
`budget` maps an effect (a layer, or `white-accent`) to a list of names where it may
appear: peaks, blocks or moments the prose of the plan names. The rest of the file is
pt-BR prose: the story of the night, peaks, moments, a palette per block, a role per
block and the rules of the night. Choreographies read it; the validator only checks the
front matter.

## Musical maps

A **musical map** says what the music of one track does, bar by bar and step by step, in the
very bar numbers a choreography uses. It is the factual half of directing a show: where the
bass comes in, where the break and the real drop are, who is singing. The choreography is the
creative half. `lightshows/maps/<artist-title-slug>.yml` (the same slug as the track's
choreography) is generated by `uv run scripts/nextrack_map.py analyze`, committed, and never
edited by hand; the tool is in [scripts/README.md](../scripts/README.md#nextrack_mappy). The
audio and the stems stay out of the repo.

**Grid.** Bars come from the SoundSwitch script's tempo map, through the compiler's own bar
grid, so a map bar is a choreography bar. The map stores `grid` (`bpm` and `downbeat` of the
first anchor, as in a choreography) plus every tempo anchor in `anchors` (`[ms, bpm]`), so tools
turn milliseconds into bars from the map alone. The finest unit is the **step**, a 1/16 note: 16
per bar. `offset_ms` is the median distance between the kick attacks and the nearest beat; when
it is over a quarter of a step the map also carries a `grid_warning`. It has two causes: the
grid is off, or the kick's attack is soft and `onsets.kick` reads late (then the grid is right
and the kick onsets sit up to a step late); check the grid against the audio.

**Voices.** The track is separated (Demucs `htdemucs`) into vocals, drums, bass and other; the
drums are split by frequency into `kick` (low band) and `perc` (the rest), so a map has five
voices: `vocals`, `kick`, `perc`, `bass`, `other`.

- `voices.<v>.bars`: one level per bar, `0`-`9`. `9` is the voice's own loud level and each
  level below is about 3 dB quieter; `0` is silence. A voice that is only bleed (its loud level
  per bar far under the mix's) reads `0` all the way, in `bars`, `steps`, `register` and
  `phrases` alike, so an instrumental's vocal stem does not light the movers.
  `entries` and `exits` list the bars where the voice comes in (after two quiet bars) and
  leaves (before two quiet bars). `perc` and `other` also have `balance`, one letter per bar:
  `L`, `l`, `c`, `r`, `R` (hard and soft sides, centre).
- `steps.<v>`: the same levels per step, in strings of 8 bars (128 characters; the last one
  shorter).
- `onsets.kick` and `onsets.perc`: per step, `.` or a strength `1`-`9`. Kicks are timed at the
  drum attack. `onsets.perc` includes the kick's click, and a quiet kick within a second before
  a louder section can be missing from `onsets.kick`.
- `register`: per step for the vocals, `.` where no pitch is heard (silence, breath, sibilance,
  any unpitched step), else `0`-`9` for the pitch within the track's own vocal range.
  `phrases` lists the vocal phrases as `from`/`to` (`bar.beat`) with a `register` (`low`,
  `mid`, `high`) and a `level`; a gap shorter than a beat does not split one.

**Sections.** Every bar has a kind, cut from the audio by the kick and the bass. The *low end*
is the two measured together (their power sum). A bar is *full* when the low end is within 6 dB
of its loud level **and** the kick and the bass are each within 15 dB of their own loud level,
so a loud kick alone is not full: the bass entering under a steady kick is a drop. A bar is
*well below* full when the low end is at least 9 dB under its loud level. Tech house often
filters the bass in a break instead of removing it, so a break need not be silent.

| kind | meaning |
|---|---|
| `intro` | from bar 1 to the bar before the first full bar (none when the track starts full), so a kick-only intro is an intro and the bass's entry is a drop |
| `groove` | full from bar 1, until the first break |
| `break` | starts with at least 2 bars well below full, after full bars, and lasts until the next full bar: bars that are neither full nor well below (the kick back before the bass) stay in it; a drop shorter than 2 bars between two breaks is a stab inside one break |
| `build` | the end of a break (2 to 16 bars) where percussion and the high end rise bar over bar, into a drop |
| `drop` | from the first full bar after the intro or after a break, until the next break |
| `outro` | after the last full bar |

`drops` lists the first bar of every drop with its size `db` (kick plus bass against the two
bars before), so a filtered bass coming back can be told from the real drop. `silences` lists
the runs of bars where the whole mix is near silent.

**Hot cues.** `hot_cues` holds the owner's rekordbox hot cues A-H, in letter order, as `bar.beat`
on the same grid (`B` is where a track enters, `G` where the next one starts to be beatmatched
over it); a cue more than 30 ms from a beat keeps its offset (`9.1+500ms`). Without rekordbox,
or when the track is not in its collection, `hot_cues` is `null` and `hot_cues_note` says why.
`nextrack_map.py cues` refreshes them without redoing the analysis.

**Stale maps.** A map is stale when the audio file's hash, the script's GUID or its tempo
anchors differ from the stored ones. `analyze` redoes a stale map; `render` warns and does not
draw a map whose anchors differ from the script's, nor, when no map has the script's GUID, the
map of the same track made from an older script.

**How a choreography reads a map.** Cut sections at the map's drops and breaks instead of
guessing them from the autoscript's 8-bar phrases (`nextrack_map.py show <track>`; for a set,
`nextrack_map.py timeline`). Bars in a map and in a choreography are the same numbers. `render`
draws the map under the simulator's timeline: section bands, five voice lanes shaded by level,
a tick per drop and per hot cue.

```yaml
# Generated by scripts/nextrack_map.py analyze. Do not edit by hand.
map_version: 1
track: Rampa, Adam Port, &ME, chuala, Keinemusik — Say What   # the pool's Artist — Title
soundswitch: 0123ABCD-0000-0000-0000-000000000000            # script GUID
audio: {sha256: 3f9c1a2b4d5e, ms: 181245}                     # first 12 hex of the file's hash, length
grid: {bpm: 120.0, downbeat: "0:00.061", anchors: [[61, 120.0]], offset_ms: -5}
separator: htdemucs
bars: 97
hot_cues: {A: "1.1", B: "26.1", G: "79.1"}                    # or `hot_cues: null` with `hot_cues_note`
voices:                                                       # the five voices, in this order
  vocals: {bars: "9999...", entries: [1, 45], exits: [33, 96]}
  kick: {bars: "9999...", entries: [1, 41], exits: [38, 94]}
  perc: {bars: "8999...", entries: [1], exits: [96], balance: "ccccl..."}
  bass: {bars: "0000...", entries: [9, 41], exits: [38, 94]}
  other: {bars: "7788...", entries: [1], exits: [96], balance: "cccc..."}
steps:                                                        # one string per 8 bars, per voice
  vocals: ["9988...", ...]
  kick: ["9711...", ...]
  perc: ["9468...", ...]
  bass: ["0008...", ...]
  other: ["7777...", ...]
onsets:                                                       # kick and perc only
  kick: ["9...9...9...9...", ...]
  perc: ["..8...8...8...8.", ...]
register: ["..567765..", ...]
phrases: [{from: "1.1", to: "8.4", register: mid, level: 8}]
sections: [{bars: [1, 38], kind: groove}, {bars: [39, 40], kind: break}, {bars: [41, 64], kind: drop}]
drops: [{bar: 41, db: 18.5}]

```

## Seeing the show

SoundSwitch has no 3D preview. `render` is the cheap way; for the real signal, SoundSwitch
can send Art-Net to a visualizer on the same Windows PC (Preferences, Hardware: enable
Art-Net and the localhost node; listen on Art-Net universe 0; start the visualizer first).
Free choices: XR_DMX_Visualiser, Capture (Student edition) and QLC+ 5. Details in
[docs/soundswitch/file-format.md](../docs/soundswitch/file-format.md#seeing-the-show).

## Schemas checked by the validator

Checked by `check_repo.py` (rules `lightshow-rig`, `lightshow-track`, `lightshow-plan`,
`musical-map`); the checks live in `scripts/lightshow.py` and `scripts/musical_map.py`. Shows
have their own rules (`show-source`, `show-rules`, `show-compiled`), described in
[shows/README.md](shows/README.md).

**`rig.yml`** (optional): exactly `room`, `fixtures` and `matrix`, with the keys above;
`kind` and `corner` from their lists; `matrix.white_max` a number in (0, 1]; a fixture of
kind `haze` has a `level` in (0, 1], and no other kind has one.

**`tracks/<artist-title-slug>.yml`**: `track` matches a pool track (same matcher as block
tracklists), `soundswitch` is a GUID, `grid` has `bpm` and `downbeat` (`m:ss.mmm`),
`sections` are sorted and do not overlap, layer names, moves, draws, rates and `#RRGGBB`
colours are from the vocabulary, and unknown option keys are findings.

**`sets/*.md`** (but `README.md`): front matter whose `set` is an existing path relative
to the repo root and whose `budget` keys are layers or `white-accent`.

**`maps/*.yml`**: exactly the keys of the example above (`grid_warning` is optional;
`hot_cues_note` is required when `hot_cues` is `null` and forbidden otherwise); `voices` and
`steps` hold exactly one entry per voice (`vocals`, `kick`, `perc`, `bass`, `other`), `onsets`
exactly `kick` and `perc`, and a voice has `bars` plus optional `entries`, `exits` and (`perc`
and `other` only) `balance`; `track` matches a pool track and the file is named
`<slug of track>.yml`; `soundswitch` is a GUID; `grid` has `bpm`, `downbeat`, `anchors` (sorted
`[ms, bpm]`, the first at the downbeat and the `bpm`) and `offset_ms`; `bars` is a positive
integer; every per-bar string has `bars` characters and every step list adds up to `bars × 16`,
from its alphabet; bar numbers and `bar.beat` values are inside `1..bars`; `sections` are
sorted, do not overlap, cover every bar and use the kinds above.
