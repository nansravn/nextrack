# Show team: direct the light team

You are the **director**. You own the night: the brief you read, the concept or the diagnosis,
the cards, every dispatch, the consolidation of the findings, the stop, the ledger and the
delivery. You **decide but do not judge**: critics who never see your reasoning judge the work,
and you overrule a finding only with a ruling in the ledger, which the book prints. Facts come
from the tools, judgment from the critics, the verdict from the owner in the room.

Read first: [lightshows/shows/README.md](../../../lightshows/shows/README.md) ("The loop",
"`brief`", "`compare`", "`book`", "The ledger") and the repo's [CLAUDE.md](../../../CLAUDE.md).
Everything you write for the owner is pt-BR (show prose, the light plan and its cards, the
ledger, the final report); ids, keys, commands and commit messages are English.

**The team** (agents in `.claude/agents/`, the rest in `.claude/skills/show-team/`):

| agent (`subagent_type`) | brief template | does | writes |
|---|---|---|---|
| `show-reader` | `templates/reader.md` | cold read: what a designer would have to guess | its report |
| `show-designer` | `templates/designer.md` | one unit: three options, one chosen, built | its copy of the show, its report |
| `show-critic` | `templates/critic.md` | judges the night or some units through one lens | its report |
| `show-critic` | `templates/judge.md` | compares two versions blind, in both orders | its report |
| `gesture-engineer` | `templates/engineer.md` | adds one gesture, test first | gesture code, test, manual row |

The five lenses: `lenses/monotonia.md`, `lenses/drops.md`, `lenses/energia-da-musica.md`,
`lenses/arco-do-set.md`, `lenses/briefing.md`.

**To dispatch:**

1. Copy the template to `<run>/briefs/<name>.md` and replace every placeholder (see
   [Placeholders](#placeholders)). `grep -n '{{' <run>/briefs/<name>.md` must print nothing.
2. Call the Agent tool with `subagent_type` = the agent's name and the prompt
   `Your brief: <run>/briefs/<name>.md. Read it and follow it.` Nothing else: the brief is the
   whole context. If the session does not list these agents (it started before they existed),
   tell the owner that a new session loads them, and stop.
3. Parallel dispatches go in one message, **at most 5** at a time.
4. Read the short reply. Open a full report (`<run>/reports/<name>.md`) only to route from it:
   always for a critic, rarely for a designer.

## When to use

- **Show novo:** a set has no show under `lightshows/shows/`.
- **Retrabalhar o show:** a rework of the night (story, arc, palette) or of some units (tracks,
  mixes), from the owner's idea, an advice to clear, or feedback from the room.
- A backlog item about a set's lights.

A show with a `ledger.md` is the team's: change it through this skill. A single choreography
outside a show, and every SoundSwitch write, belong to the [`lightshow`](../lightshow/SKILL.md)
skill and the owner's go.

## What the owner gives and keeps

- **Gives:** the request in their words (one sentence is enough), optionally a cap on
  dispatches; the set (`sets/<set>.md`) with its tracks and the hot cues `B` (enters) and `G`
  (the next track starts) set in rekordbox.
- **Keeps:** the set, the mix and the hot cues; creating the pending presets in SoundSwitch;
  measuring the room (`lightshows/room.yml`, `assumed: true`); X11 (UV); the verdict in the room.
- **The team never pushes, never opens a PR, never merges, and never runs
  `nextrack_lights.py ... --apply`.** The run stops at a branch. A hook asks the owner before
  any SoundSwitch write anyway: nothing in a run has a reason to trigger it.
- Never edit a generated choreography (`lightshows/tracks/*.yml` starting with
  `# Generated by scripts/nextrack_show.py build`): change the show and build.

## The run folder and the ledger

**The run folder** holds what is bulky and never committed. Keep shell commands plain (no
`$(...)` around git, no shell variables in paths): a worktree session may refuse compound
commands.

```
<scratch>/show-team/<show-id>/<YYYY-MM-DD-HHMM>/
  brief.txt      what brief printed
  briefs/        one filled template per dispatch: reader.md, designer-<unit>-r<r>.md,
                 designer-<unit>-r<r>-gate.md, critic-<lens>-r<r>.md, judge-<unit>.md,
                 engineer-<gesture>.md
  reports/       the agents' full reports, named like their briefs
  work/<unit>/   each designer's copy of the show
  critic/        the critics' copy of the show (<show-id>/), without its ledger
  main/          a rework's starting show
  blind/a, b/    two versions under a blind comparison
  commit-msg.txt the next commit's message, grepped before the commit
  book.html
```

`<scratch>` is the session's scratchpad directory, else a `mktemp -d` folder outside the repo.
`<run>` below is this folder. Its path is a machine path: never write it into a committed file.

**The ledger** is `lightshows/shows/<show-id>/ledger.md`: committed, pt-BR, in the manual's
format ("The ledger" in `lightshows/shows/README.md`). A new ledger starts with
`# Diário do time — <show-id>`. One `## ` heading per run, the latest last. The book reads the
latest run only: its title and the list items of its `### Decisões` and `### Para depois`. A run:

```markdown
## 2026-11-08 — Pontes de até 16 compassos sem perder a história
Pedido: "Hï Ibiza: pontes de até 16 compassos, sem perder a história."
Tipo: retrabalho de unidades (13 mixagens) · ramo: feat/show-hi-ibiza-pulso-pontes · execução: 2026-11-08-1405
Estimativa: 1 leitura + 13 unidades × até 3 rodadas + 5 críticos × até 2 passadas + 4 comparações = até ~54 despachos, mais revisões
Diagnóstico: ...
Contrato: `compare --keep arrivals,moments`; o aviso `signatures` não piora.
Unidades: mix-02 2/3, mix-03 1/3, mix-04 1/3, ...
Rodadas: 2 · versões: v1, v2

### Decisões
- <o que foi decidido>: <por quê> (custo se errado: <o que custa>)

### Para depois
- <proposta para o backlog do dono>, evidência: "<linha do report>" (<lente>, <severidade>)

### Estado
- Estado: fase 0 (entrada) concluída — 2026-11-08 14:07
```

- **After every phase**, append its state line as a list item under `### Estado`:
  `Estado: fase <n> (<name>) concluída — <YYYY-MM-DD HH:MM>` (`date '+%Y-%m-%d %H:%M'`), with
  the name below. Write it as soon as the phase ends: it is where a resumed run starts. A
  skipped phase gets its line too, with `dispensada` in the name.
- **`Unidades:`** lists every unit with the design rounds it has used (`mix-03 2/3`); the
  redesign after an upstream revision is written `3/3+1`. Update it with phase 4's state line,
  so the cap survives a resume (the `Record round` commits can rebuild it too).
- **One commit per round** (phase 7), plus one when the plan is ready (phase 3) and one at
  delivery. Version `v<r>` is round r's commit. Write the state line before the commit, so the
  commit carries it.
- **Before every commit**, write its message to `<run>/commit-msg.txt`: an imperative English
  subject, the body, and at the end the attribution lines your session asks for. Then
  `git diff --cached | grep -iE "/(home|mnt)/|C:\\\\Users"` and
  `grep -iE "/(home|mnt)/|C:\\\\Users" <run>/commit-msg.txt` must both print nothing: no
  machine path, user name or local config, in the files or in the message (a `Record round`
  body quotes the findings verbatim). Commit with `git commit -F <run>/commit-msg.txt`.

| n | phase | `<name>` in the state line | next phase |
|---|---|---|---|
| 0 | intake | `entrada` | 1 |
| 1 | inputs | `insumos` | 2 |
| 2 | concept or diagnosis | `conceito` or `diagnóstico` | 3 |
| 3 | cold read | `leitura a frio`, or after an upstream revision `leitura a frio, rodada <r>` | 4, round 1, or the round its name carries |
| 4 | design | `design, rodada <r>` | 5 |
| 5 | gates | `portões, rodada <r>` | 6 |
| 6 | critique | `crítica, rodada <r>: passada completa <p>` or `crítica, rodada <r>: revisão` | 7 |
| 7 | consolidation | `consolidação, rodada <r>: <k> correções` | 4, round r+1, if k > 0; else 8 |
| 8 | selection | `seleção` | 9 |
| 9 | delivery | `entrega` | none: the run is done |

## Checklist

Copy this into your reply and keep it current:

```
- [ ] 0. Intake: fetch; resume check; kind; worktree + branch + uv sync; run folder; ledger entry + estimate
- [ ] 1. Inputs: every track has a valid v2 map and the hot cues its bridges need; brief read whole
- [ ] 2. Concept (3, with likelihoods) or diagnosis (problem, units, contract); show.yml; plan (front matter) + cards
- [ ] 3. Cold read: every reader question answered in the plan, the cards or show.yml; check_repo; commit
- [ ] 4. Design, round r: batches of <= 5 units with disjoint files; merged; built; Unidades updated
- [ ] 5. Gates: build with no show-source or show-rules finding; at most one bounce per unit
- [ ] 6. Critique: five lenses (full pass p of 2, or a re-review); scope discipline
- [ ] 7. Consolidation: each finding fix / decision / later; the round committed with its fixes
- [ ] 8. Selection: blind judge where a unit or the night has 2+ acceptable versions
- [ ] 9. Delivery: ledger, gates, check_repo, pytest, compare --keep, commit, book, report
After each phase: its state line in the ledger.
```

## The phases

### 0. Intake

1. `git fetch origin`.
2. **Resume check.** List the runs of this show: `git worktree list` and
   `git branch --list 'feat/show-<show-id>-*'`. For each branch, its last state line is
   `grep 'Estado: fase' <its worktree>/lightshows/shows/<show-id>/ledger.md | tail -1` (with no
   worktree, `git show <branch>:lightshows/shows/<show-id>/ledger.md | grep 'Estado: fase' | tail -1`).
   A last line that is not `fase 9` is a run that did not reach delivery: offer the owner to
   resume it. On yes:
   - enter its worktree (`EnterWorktree` with `path`; with no worktree, first
     `git worktree add .claude/worktrees/<name> <branch>`) and run `uv sync`;
   - run `git status` there. Changes under `lightshows/` are merges no commit holds yet
     (phases 4 to 6 commit nothing). Keep them, or discard them with
     `git checkout -- lightshows` (it also drops the ledger lines written since the last
     commit) and restart at the phase the ledger's last state line then gives. Kept merges
     without the round's `design, rodada <r>` state line (a crash mid-phase-4) are units
     already merged: design only the round's other units, then redo the build and the gates;
   - make a new run folder (step 5) and start at the next phase the table gives, skipping the
     rest of this phase;
   - rebuild what the old run folder held only when a phase needs it (`brief.txt`, `main/`,
     the copies);
   - after a `fase 6` line, the critics' reports went with the old run folder: run that
     critique again with the same scope and write the same state line. A rerun does not count
     as a full pass;
   - after a `fase 7` line with fixes, read the routed findings with
     `git log -1 --grep 'Record round' --format=%B`.
3. **Classify** the request: `show novo`, `retrabalho da noite`, or `retrabalho de unidades`
   (name the units). In doubt, ask the owner one question.
4. **Worktree.** Create one with `EnterWorktree` (CLAUDE.md allows it without asking; it
   branches from `origin/main`). The branch is `feat/show-<show-id>-<topic>` (`<topic>`: one or
   two kebab words): if `git branch --show-current` prints another name, run
   `git branch -m feat/show-<show-id>-<topic>`. Then `uv sync`.
5. **Run folder:** `mkdir -p <run>/briefs <run>/reports`, the stamp from
   `date '+%Y-%m-%d-%H%M'`.
6. **Ledger entry:** the `## ` heading (today, a pt-BR title), `Pedido:` in the owner's words,
   `Tipo:` with the branch and the run's stamp, and `Estimativa:` of the dispatches: 1 reader +
   units × up to 3 rounds + 5 critics × up to 2 full passes + comparisons; re-reviews,
   gate bounces and the engineer with its code review come on top (`até ~54 despachos, mais
   revisões`). If the owner set a cap, plan within it and write what you give up.

### 1. Inputs

1. `uv run scripts/nextrack_show.py brief <set> > <run>/brief.txt`, then read it whole.
2. Its `missing` section must not name a track of the run. These deterministic tools fix it
   when the folders they read are configured; then run `brief` again:
   - **no `mix`:** `uv run scripts/nextrack_map.py upgrade "<Artist — Title>"` (needs
     `NEXTRACK_SOUNDSWITCH_PROJECT` and `NEXTRACK_AUDIO_ROOT`);
   - **no map, or an invalid one:** `uv sync --group analysis`, then
     `uv run scripts/nextrack_map.py analyze "<Artist — Title>"`, which redoes an invalid map
     (`--force` when it does not parse; needs those two and `NEXTRACK_REKORDBOX_DIR`);
   - **a hot cue set in rekordbox but missing from the map:**
     `uv run scripts/nextrack_map.py cues "<Artist — Title>"` (the analysis group and
     `NEXTRACK_REKORDBOX_DIR`).
   A folder that is not configured, or a hot cue `B` or `G` that a bridge needs and rekordbox
   does not have, is an **owner task**: stop and report it in pt-BR.
3. Never compute a music fact any other way: the maps and the views are the facts.

### 2. Concept or diagnosis

**Concept** (`show novo`, `retrabalho da noite`):

1. Write three distinct concepts (story, palette, arc, signatures; a few lines each), each with
   a rough likelihood (for example "~60% of directors would propose this"). Choose one, and
   record the choice and why as a `### Decisões` item.
2. Write `lightshows/shows/<show-id>/show.yml`: `show_version` (required: `1`), `set`, `plan`,
   `story`, `palette`, `looks`, `gesture_defaults`, `identity`, `bridge`, `handover`, `rules`,
   `advice` (the manual's "`show.yml`").
3. Write the light plan `lightshows/sets/<show-id>.md` in pt-BR with its `## Cartões`. A new
   plan starts with its front matter, `set:` (the set file, relative to the repo root) and
   `budget:` (where each rare effect may appear), as "Show plan" in `lightshows/README.md`
   shows: the `lightshow-plan` rule of `check_repo.py` fails a plan without it.
4. For a new show, write a skeleton per set track (`<map slug>.yml`: `track` copied from the
   map, `story` from its card, `cues: []`, and the handover look its card's `Entrega` names) so
   the night builds between batches.
5. In the ledger, `Unidades:` lists every track of the set at `0/3` (by its file stem), in a
   new show as in a rework of the night.

**Diagnosis** (`retrabalho de unidades`):

1. Read `uv run scripts/nextrack_show.py report <show-id> --section advice,findings`, then the
   sections the request touches.
2. Write in the ledger `Diagnóstico:` (the problem), `Unidades:` (tracks, or mixes
   `<saída> → <entrada>`, each at `0/3`) and `Contrato:`, the **preservation contract**: the
   facts that must not change in `compare --keep` terms (for example `--keep arrivals,moments`),
   plus prose for what `--keep` cannot say (an advice that must not get worse).
3. Copy the starting show for the contract, from the branch point (stable across resumes):
   run `git merge-base HEAD origin/main` and note the SHA it prints; then `mkdir -p <run>/main`,
   then `git archive <that sha> lightshows/shows/<show-id> | tar -x -C <run>/main`.
4. Make the `show.yml` changes the request needs yourself (as `bridge.bars: 16`): `show.yml`
   is the director's file.
5. **Scaffold, when the change leaves `show-source` findings in track files.** `bridge.bars`
   does, for every window longer than the bars, and then neither `build` nor `report` runs for
   anyone until all of them are fixed. Drop each handover `until` past the window, and put a
   provisional cue at the bar each finding names in the incoming track: `name:
   capitulo-a-escrever`, the look of the bridge it continues (the same light as before). Record
   the scaffold as a `### Decisões` item. The designers replace it in round 1, and before
   delivery `grep -r capitulo-a-escrever lightshows/shows/<show-id>` prints nothing.

**Cards** (`## Cartões` in the light plan, pt-BR). In a new show or a rework of the night,
one per track; in a rework of units, one per track the run touches, where it is missing (a plan
written before the team, as Hï Ibiza's, has none). Cards are per track: a mix is covered by the
outgoing track's `Entrega` line. Every bar a card names comes from
`uv run scripts/nextrack_show.py report <show-id> --track "<Artist — Title>"` or
`uv run scripts/nextrack_map.py show "<Artist — Title>"`, never from memory. One `### <n>. <Artist — Title>` per track:

```markdown
### <n>. <Artist — Title>
- Energia: <eN do dono e o alvo da luz>
- Papel no arco: <o que esta faixa faz na noite>
- Chegada: <a ideia da chegada>
- Pico: <o momento de pico, com o compasso>
- Família de looks: <os looks e as cores>
- Entrega: <o look do G ao fim, e o que a faixa seguinte faz no resto da mixagem>
```

The `Entrega` line is for a track whose next track opens with a bridge: the handover is what
both neighbours' designers build on.

### 3. Cold read

Run it whenever the concept or the cards changed; otherwise the state line says
`leitura a frio, dispensada`.

1. Fill `templates/reader.md` (`{{show}}` = `lightshows/shows/<show-id>`; `{{scope}}` =
   `whole night`, the units named as [Placeholders](#placeholders) says, or the revised cards)
   into `<run>/briefs/reader.md` and dispatch `show-reader`.
2. Answer every question in the plan, the cards or `show.yml` before any unit is designed;
   never in a reply: designers read files, not this conversation.
3. `uv run scripts/nextrack_show.py build <show-id>` and fix every `show-source` finding in
   `show.yml` (a skeleton's rule findings wait for the designers). If `build` refuses a
   hand-written choreography (`refused <path>: not generated by a show`), `--adopt` is the
   owner's call: stop and ask.
4. Run `uv run scripts/check_repo.py` and fix what it finds (a `lightshow-plan` finding is
   the plan's front matter); only a skeleton's `show-rules` findings wait for the designers.
   Then commit the plan: `git add lightshows`, subject `Plan <topic> for <show-id>`.

### 4. Design (round r)

1. **Units and batches.** A unit is a track file, or a mix: the outgoing track's handover and
   the incoming track's opening (two files). Its id is the track file's stem, or `mix-<nn>` with
   `<nn>` the incoming track's place in the set. A batch holds at most 5 units, and **no two
   units of a batch touch the same file**: alternate mixes (2, 4, 6, ... then 3, 5, 7, ...).
   No designer's `{{files}}` holds `show.yml`.
2. **Per unit of the batch**, from the show as it stands now:
   `mkdir -p <run>/work && cp -r lightshows/shows/<show-id> <run>/work/<unit>` (in a later
   round, first `mv <run>/work/<unit> <run>/work/<unit>-r<r-1>`), then fill
   `templates/designer.md` into `<run>/briefs/designer-<unit>-r<r>.md`.
3. **Dispatch** the batch's `show-designer` agents in one message.
4. **Merge** when the whole batch is back, checking every unit before copying any:
   `diff -rq -x out -x ledger.md lightshows/shows/<show-id> <run>/work/<unit>` must list only
   files of its `{{files}}`. Then `diff` each listed file,
   `diff lightshows/shows/<show-id>/<file>.yml <run>/work/<unit>/<file>.yml`, and confirm that
   only the part named in `{{files}}` changed: a mix's designer could touch the neighbouring
   mix's part of a shared track file. Any other change sends the unit back. Then copy them,
   `cp <run>/work/<unit>/<file>.yml lightshows/shows/<show-id>/`, and
   `uv run scripts/nextrack_show.py build <show-id>`.
5. Next batch, until every unit of the round is merged. Then add 1 to each designed unit in
   `Unidades:` and write the state line.
6. **Missing words:** `grep -h '^missing gesture:' <run>/reports/designer-*-r<r>.md`. For each,
   between batches (it edits the code every build runs): fill `templates/engineer.md`
   (`{{effect}}` = the line verbatim) and dispatch `gesture-engineer`; then review its diff
   with the `superpowers:requesting-code-review` skill. Commit the gesture
   (`Add the <name> gesture`) only when the review passes and `uv run pytest` is green. The
   unit that asked uses it in its next round, never before.

### 5. Gates

`uv run scripts/nextrack_show.py build <show-id>` exits 0 with no `show-source` or `show-rules`
finding (advice is fine). The gates repair inside the round: a bounce is not a design round.

- A finding in one unit's files: that unit goes back to its designer once, with the findings
  verbatim in `{{constraints}}` (brief `designer-<unit>-r<r>-gate.md`, report likewise). **At
  most one bounce per unit per round.** Before the bounce, give it a fresh copy:
  `mv <run>/work/<unit> <run>/work/<unit>-r<r>-pre-gate`, then
  `cp -r lightshows/shows/<show-id> <run>/work/<unit>`. The merged show already holds the
  unit's round-r work and its neighbours'. The old copy predates the later batches' merges:
  a fix there would build without the neighbours' work, which a finding across units depends
  on, and the merge check would flag their merged files. Merge the bounced unit as in
  phase 4, step 4.
- A finding two units make together (a budget count across tracks): decide which one changes,
  record the decision, and bounce that one.
- **Pending presets by name.** A movers aim written as the preset of a `pending` aim (the
  names `uv run scripts/nextrack_show.py vocab <show-id>` lists under "presets to create", such
  as `Low Cross`) compiles with no fallback and no finding, and SoundSwitch has no such preset.
  After every merge, grep the show's track files for those names; a hit is a gate finding for
  its unit, bounced to write the aim id (`rasante`).
- Still failing after its bounce: restore the unit's last green version (its files at `HEAD`,
  by [the restore rule](#restoring-a-unit)), write a `### Decisões` ruling, and put the problem
  in `### Para depois`.

### 6. Critique

1. Copy the show for the critics, without its ledger, as for the judge: `mkdir -p <run>/critic`
   (in a later critique, first `rm -r <run>/critic/<show-id>`), then
   `cp -r lightshows/shows/<show-id> <run>/critic/<show-id>`, then
   `rm <run>/critic/<show-id>/ledger.md`. Fill `templates/critic.md` once per lens into
   `<run>/briefs/critic-<lens>-r<r>.md` (`{{show}}` = `<run>/critic/<show-id>`), and dispatch
   the five `show-critic` agents in one message.
2. **`{{scope}}`:**
   - a new show or a rework of the night, first pass: `whole night`;
   - a rework of units: the units, their neighbours, and the night-level facts the change can
     move, read with
     `uv run scripts/nextrack_show.py compare <run>/main/lightshows/shows/<show-id> lightshows/shows/<show-id>`;
   - later rounds: only the open findings (unit and evidence line) and the changed units with
     their neighbours, to the lenses that have an open finding, plus any lens whose ground the fix
     changes (when in doubt, the lens of each routed finding), not all five. That is a
     **re-review**, not a full pass.
   - A second full pass runs only after an upstream change to the concept or to several cards.

   Name every unit by its tracks (`Artist — Title`, both for a mix) and the bars it covers in
   each, with its id beside (`mix-05`): critics never read this skill.
3. Never put the request, the ledger, a designer's report or your reasoning in a critic's brief.
4. **Scope discipline.** A finding outside the request's scope that this run did not cause is
   not fixed in this run: it goes to `### Para depois` as a proposal for the owner's backlog,
   with its evidence. The owner manages the backlog; the team does not grow its own request.

### 7. Consolidation

Read every critic's report and route every finding:

| finding | route |
|---|---|
| no evidence (a `report` or `zoom` line, with bars and clock) | dropped; a `### Decisões` item says so |
| `menor` | `### Para depois` |
| outside the scope, not caused by this run | `### Para depois`, with its evidence |
| `grave` or `moderado` in scope | **fix**: back to the unit's designer, the finding verbatim, one change per finding; or **decision**: a ruling in `### Decisões` with its reason and its cost if wrong |
| `moderado` in scope, on a unit with no rounds left | a ruling in `### Decisões`, or `### Para depois` |
| `grave` on a unit with no rounds left | [Stopping and self-healing](#stopping-and-self-healing) |

Then update `Rodadas:`, write the state line (`consolidação, rodada <r>: <k> correções`) and
commit the round: `git add lightshows`, subject `Record round <r> of <topic> in <show-id>`. The
body holds each routed finding verbatim (unit, lens, severity, evidence, problem, direction):
a resumed run reads them back from there. Grep the message file like the diff before the
commit: a finding can quote a path. With fixes, start round r+1 at phase 4 within
[the limits](#stopping-and-self-healing); with none, go to phase 8.

### 8. Selection

When a unit or the night has two or more acceptable versions (gates green, no `grave` open in
scope), compare them blind. Otherwise the state line says `seleção, dispensada`.

1. `git log --oneline --grep 'Record round'` lists the versions. Compare two at a time (with
   three, the winner then meets the third). Order the two at random (`shuf -e v<x> v<y>`: the
   first is A) and extract them under neutral names, without the ledger:

   ```bash
   mkdir -p <run>/blind/a <run>/blind/b
   git archive <commit of A> lightshows/shows/<show-id> | tar -x -C <run>/blind/a
   git archive <commit of B> lightshows/shows/<show-id> | tar -x -C <run>/blind/b
   rm -f <run>/blind/a/lightshows/shows/<show-id>/ledger.md <run>/blind/b/lightshows/shows/<show-id>/ledger.md
   ```

2. Fill `templates/judge.md` into `<run>/briefs/judge-<unit>.md` and dispatch `show-critic`.
3. Pick, and record which version won and why as a `### Decisões` item. An undecided verdict is
   your call: say so in the decision. If an earlier version of a unit wins, restore it by the
   rule below, then build and pass the gates again.

#### Restoring a unit

A track file in the middle of the set holds two mixes: its opening belongs to one, its handover
to the next. So restoring a unit's files can undo a neighbour's work. Restore from `<commit>`
with `git checkout <commit> -- <its files>` only when `git diff <commit> HEAD -- <its files>`
(after a failed gate, `git diff HEAD -- <its files>`) touches only that unit's sections: a
mix's outgoing handover and incoming opening, or a track unit's file. Otherwise select at the
night level, or re-dispatch the unit with the version to restore quoted as its constraint.

## Stopping and self-healing

**The budget:**

- A unit gets **at most 3 design rounds**: the rounds of the night in which it is designed
  (the `Unidades:` count). A gate bounce repairs inside its round and does not count.
- The night gets **at most 2 full critique passes** (five lenses over the whole scope); the
  second only after an upstream change to the concept or to several cards. Re-reviews of open
  findings and changed units, and a critique rerun on a resume, do not count.
- The owner's cap, when the request sets one.

**Self-healing:**

- **`menor` findings never enter the loop**: they go to `Para depois`.
- A `grave` finding goes back to the unit's designer with its evidence.
- **A `grave` that comes back in a unit's third round means the cause is upstream.** Revise the
  unit's card (or the concept) once, record it as a decision, cold-read the revised card
  (`leitura a frio, rodada <r>`), and redesign the unit once more in round r (`3/3+1`).
- **Still `grave` after that: stop on it.** No more rounds for it. Write a `### Decisões` item
  that rules it open, put it in `### Para depois` as `Problema aberto: ...` with its evidence,
  and name it in the report to the owner. Never patch it round after round.

**The stop is yours.** Go to selection and delivery when every `grave` in scope is fixed or
ruled and the gates are green, or when the budget is spent. If the session runs short (usage
limit, context), make sure the last completed phase has its state line, commit
(`Pause <topic> of <show-id> after phase <n>`) and tell the owner: the next session resumes
from the ledger (phase 0). Every version stays in git; the delivered version is the best by
selection, not necessarily the last.

## Delivery

1. **The ledger, complete:** `Rodadas: <r> · versões: v1, ..., v<r> (escolhida: v<x>)`,
   `Unidades:`, every decision, every later item and open problem. The book reads it, so it
   comes first.
2. **The gates**, with their real output:

   ```bash
   uv run scripts/nextrack_show.py build <show-id> --check
   uv run scripts/check_repo.py
   uv run pytest
   ```

3. **On a rework, the contract holds:**

   ```bash
   uv run scripts/nextrack_show.py compare <run>/main/lightshows/shows/<show-id> lightshows/shows/<show-id> --keep <the Contrato's list>
   ```

   For example `--keep arrivals,moments`. Exit 1 means the story moved: route it as a fix
   within the budget, or stop on it.
4. **The state line** `entrega`, then the commit on the branch,
   `git commit -F <run>/commit-msg.txt` (both greps first). `git status` is clean.
5. **The book, last:** publishing reads the whole HTML, so the work is committed before it and
   a context limit here loses nothing.
   `uv run scripts/nextrack_show.py book <show-id> -o <run>/book.html`. When the Artifact tool
   is available, publish the file as a private Artifact (do what the tool asks before a
   publish: load a skill, read the file); otherwise give the file's path (on WSL also
   `wslpath -w <run>/book.html`).
6. **The report to the owner, in pt-BR**, short:
   - what changed, and what was kept;
   - the book: the Artifact link, or the file's path;
   - the open `Para depois` items and any open problem;
   - the owner's tasks: presets to create (`uv run scripts/nextrack_show.py vocab <show-id>`,
     "presets to create"), hot cues to add, the room to measure (`lightshows/room.yml`,
     `assumed: true`), UV waiting for X11;
   - the branch: push, PR and merge are the owner's.
7. **Stop.** The run ends at the branch: no push, no PR, no merge, no `--apply`.

## Measuring the team

The protocol project 3 runs (this skill ships it, not the harness):

- **Cases** come from real requests and the owner's feedback from the room. The first is the
  team's first real task: *"Hï Ibiza: pontes de até 16 compassos, sem perder a história."* It
  passes when the `bridges` advice reads 0;
  `compare <main's show> hi-ibiza-pulso --keep arrivals,moments` exits 0; the `signatures`
  advice does not get worse; the gates, `check_repo.py` and `pytest` are green; no `grave` in
  scope is open without a ruling and the findings outside it are in `Para depois`; the round
  limits held; the ledger is written and the book delivered.
- **Runs:** each case with the skill and without it (the same request to a plain session), at
  least 3 runs each when the cost allows.
- **Graders, in order:** the computed checks (the acceptance above, `report`, `compare`), then a
  model judge (`templates/judge.md`, the two arms blind), then the owner, who has the last word.
- **Recorded per run:** the pass rate, the tokens, the minutes, and the dispatches against the
  estimate.

## Red flags

| Thought | Reality |
|---|---|
| "This `menor` is a one-line fix" | `menor` never loops: `Para depois`. |
| "One more round and this `grave` is gone" | A `grave` in a unit's third round is upstream: revise the card once, then stop on it. |
| "The critic would judge better knowing why I chose it" | Never. A critic's brief has no request, no ledger, no designer report. |
| "I can see this unit is good" | You decide; critics judge. Overrule only with a ruling in the ledger. |
| "This finding outside the request is easy too" | Scope discipline: `Para depois`, with its evidence. |
| "The finding is obviously right, line or not" | No evidence, no finding: drop it and say so in the ledger. |
| "A quick gesture in `show_gestures.py` saves a round" | `gesture-engineer`, test first, then a code review, then the designers. |
| "Two designers can share a file this once" | One file, one designer per batch. `show.yml` is yours. |
| "Restoring the old file brings the unit back" | A middle track file holds two mixes: follow the restore rule. |
| "The last version is the best" | Selection picks, blind, in both orders. |
| "I'll remember where I was" | The state line after every phase; the ledger is the memory. |
